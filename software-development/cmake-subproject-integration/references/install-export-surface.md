# The install/export surface of an embeddable library

The half of embeddability that `add_subdirectory` probes never touch: what the
consumer sees after `cmake --install` and `find_package`. Audit it with a scratch
consumer project, never by reading the export file alone.

## What to inspect in the installed tree
- Layout: public headers under `include/<name>/` (plus any configured header
  generated in the build tree), libraries under `lib/` (`bin/` for DLLs), package
  files under `lib/cmake/<name>/`.
- `install(DIRECTORY include/ ...)` copies *everything* under `include/`, not only
  headers: a stray `notes.md`, an editor backup `core.hpp.bak`, or test data ends
  up in the consumer's prefix next to the public headers (probed). Constrain it
  with `FILES_MATCHING PATTERN "*.h" PATTERN "*.hpp"` — two patterns, since a
  single `"*.h*"` also matches `.html`; nested directories and generated headers
  keep working, and any header the project adds later still installs. The installed
  LICENSE belongs in `${CMAKE_INSTALL_DOCDIR}` (`share/doc/<name>/LICENSE`, the
  libuv shape), which is what packagers look for; state the full installed-contents
  list in the README so "what lands in my prefix" is not a discovery.
- `<name>Targets.cmake`: `INTERFACE_INCLUDE_DIRECTORIES` must be non-empty and
  resolve to `${_IMPORT_PREFIX}/include`; `INTERFACE_LINK_LIBRARIES` must contain
  no third-party targets; `INTERFACE_COMPILE_FEATURES` / `INTERFACE_COMPILE_DEFINITIONS`
  should carry exactly the published requirements and nothing else.
- `<name>Config.cmake`: generated by `configure_package_config_file` with
  `@PACKAGE_INIT@` and a closing `check_required_components`. Add
  `find_dependency(...)` calls here for anything the export legitimately publishes.
- `<name>ConfigVersion.cmake`: check the compatibility policy and where the
  version came from — a version taken from a versioned `project()` call is the
  subproject's tree-global leak, not a choice. A version kept in project-scoped
  variables and fed to `write_basic_package_version_file` installs identically
  (`PACKAGE_VERSION`), so fixing the leak costs nothing at the consumer.
- The policy must match the version's *semantics*, and `SameMajorVersion` is
  wrong below 1.0: at major 0 the minor field is the breaking axis, yet a
  `0.2.0` package satisfies `find_package(<lib> 0.1)` because the major still
  matches. Probe it without building anything: copy the installed prefix,
  rewrite the single `set(PACKAGE_VERSION "x.y.z")` line in the installed version
  file, and configure a consumer that only runs
  `find_package(<lib> <req> QUIET)` for two requests — the older request must come
  back `NOTFOUND`. Use `SameMinorVersion`, or state the 0.x policy explicitly.
- Grep the export for the build directory path: an absolute build-tree path is the
  signature of a property that skipped `$<INSTALL_INTERFACE:...>`.

## Export-file quirks that are not defects
- `$<BUILD_INTERFACE:...>`-wrapped PRIVATE link items survive into the export as
  empty `$<LINK_ONLY:>` entries (two of them for two wrapped interface targets).
  Consumers configure, build and run fine; do not "fix" it by dropping the
  `BUILD_INTERFACE` wrapper — that is what exports the build-only needs.
- A consumer that only names the target without calling into it may record no
  import at all, so a broken export can look healthy. Make the probe consumer
  reference a real symbol from each public header it claims to support.
- An installed static library whose implementation uses a header-only third-party
  library links for the consumer with no extra dependency; the moment that
  dependency becomes compiled, the consumer gets undefined symbols. Verify the
  link actually exercises the implementation path (e.g. the function that wraps
  the third-party type), not just a leaf function.

## Installing a dependency target in your own export set
- `install(TARGETS mylib <dep> ...)` validates the dependency's target properties
  against your destination list: a dependency that sets `PUBLIC_HEADER` (fmt does,
  unconditionally, whatever its own install option says) with no
  `PUBLIC_HEADER DESTINATION` raises an author warning, and a parent configuring
  with `-Werror=dev` fails there. Clear it right after you name the dependency —
  `set_target_properties(<dep> PROPERTIES PUBLIC_HEADER "")` — instead of adding a
  destination for headers no consumer includes.
- Expect the exported dependency target to carry
  `INTERFACE_INCLUDE_DIRECTORIES ${_IMPORT_PREFIX}/include` even when you install
  none of its headers: that is the residue of the dependency's own property, it is
  harmless, and it is a README line, not a fix. Verify that README line instead of
  asserting it — a consumer that includes `<dep/header.h>` after
  `find_package(<lib>)` must fail with `file not found`, which is the evidence for
  "do not include the dependency's headers; the target carries its library only".
  If that probe *succeeds*, the header resolved from somewhere else in the tree and
  the export does not say what the README claims.
- Installing the dependency means the consumer gets whatever you built and cannot
  pin it — no `find_dependency` can help. State that contract in the README.

## Symbol visibility: the ELF half of the API macro
- A `__declspec(dllexport/dllimport)` macro is a no-op off Windows, so a library
  that guards only for `_WIN32` exports every symbol of its shared object,
  private implementation details included: on a template whose only private type
  lived under `src/`, `nm -D --defined-only lib<name>.so` listed 10 dynamic
  symbols, among them the private `<ns>::detail::options` object.
- Fix it with target properties (`CXX_VISIBILITY_PRESET hidden`,
  `VISIBILITY_INLINES_HIDDEN ON`) plus `__attribute__((visibility("default")))`
  in the API macro for the shared case. Same tree after the fix: 6 dynamic
  symbols, the private one gone, static build and Windows behaviour unchanged;
  the property is not exported, so the consumer's own TUs keep their default
  visibility.
- Export every type that crosses the boundary, not only functions. A public
  *exception* class the consumer catches needs its typeinfo exported, or the
  catch misses the type at runtime — and only the shared run shows it, because
  the static build links one copy of everything. Run `ctest` against the shared
  build with the test binary as its own DSO.
- Prove the surface with `nm -D --defined-only <lib>.so | c++filt | sort` before
  and after, not with the header list.

## Per-config artifacts in one install prefix
- Installing Debug and Release into the same prefix overwrites the DLL and the
  import library: both configs write the same unversioned file name on Windows
  (measured: Debug 400384 B replaced by Release 29184 B), while a dependency that
  ships `DEBUG_POSTFIX` keeps `fmt.dll` and `fmtd.dll` side by side. The ELF side
  is unaffected when the library carries `VERSION`/`SOVERSION`, so this one only
  shows on a Windows probe.
- Set `DEBUG_POSTFIX`, or document one install prefix per config. Package
  managers install per-config, so a consumer that Debug-links a Release-only
  install hits the `_ITERATOR_DEBUG_LEVEL` mismatch instead.
- Verify coexistence the way a multi-config generator would, in one prefix:
  `cmake --build <b> --config Debug && cmake --install <b> --config Debug`,
  then the same two commands with `Release`, then one consumer per config
  (`cmake -B c-<cfg> -DCMAKE_PREFIX_PATH=<prefix>` + `--build --config <cfg>` +
  run). Read the evidence out of the installed tree, not the build tree:
  `*Targets-debug.cmake` must carry `IMPORTED_LOCATION_DEBUG`/`IMPORTED_IMPLIB_DEBUG`
  naming the postfixed artifact while `*Targets-release.cmake` names the plain one
  (probed: `bin/<name>d.dll` + `lib/<name>d.lib` next to `bin/<name>.dll` +
  `lib/<name>.lib`), and the Debug consumer's generated project must reference the
  `d` import library. Grep the generated `*.vcxproj`'s `AdditionalDependencies`
  per condition rather than trusting the log line your own script printed.

## Consumer-side verification
1. Configure a scratch consumer with `-DCMAKE_PREFIX_PATH=<prefix>` against the
   static install, build, run.
2. Repeat against the shared install; run once with the library's `bin/` absent
   from `PATH` (expect 127 / `0xc0000135`) and once present (expect 0). From
   git-bash add it in MSYS form (`/c/...`): a native `C:/...` entry in the
   colon-separated `PATH` is not honoured and the run keeps failing with 127.
3. If the library ships third-party DLLs of its own, check `install(RUNTIME_DEPENDENCY_SET)`
   / `install(IMPORTED_RUNTIME_ARTIFACTS)` instead of a hand-rolled copy.
4. Shared installs also need a version story: without `VERSION`/`SOVERSION` on the
   library target there is no SONAME on ELF, so report the missing ABI-version knob
   rather than treating it as packaging. Set both (`VERSION ${PROJECT_VERSION}`,
   `SOVERSION ${PROJECT_VERSION_MAJOR}`) and prove the result from the *installed
   export*, not from the source: `IMPORTED_SONAME_RELEASE "lib<name>.so.<major>"`
   with `IMPORTED_LOCATION_RELEASE ".../lib<name>.so.<x.y.z>"`, and the
   `lib<name>.so -> .so.<major> -> .so.<x.y.z>` chain present in both the build tree
   and the install tree. A static build ignores both properties, so the static
   layout is unchanged — say that when proposing the change, since it is the usual
   objection. A Windows host cannot show any of it (the DLL name stays unversioned
   and `IMPORTED_SONAME` is absent), so run this probe on an ELF toolchain; sharing
   one CPM source cache across the Windows/Linux boundary makes CPM warn
   `Cache for <dep> ... is dirty`, which is a cross-filesystem artifact, not a
   finding about the project.

## When the superproject exports its own targets
- A parent that runs `install(TARGETS parentlib EXPORT parentTargets)` with
  `parentlib` linking your target needs your target to be in *some* export set,
  or the parent's configure fails with `requires target "<lib>" that is not in
  any export set` — even when the parent never installs you. Probe it directly:
  a parent with `install(TARGETS ... EXPORT ...)` and a `PUBLIC` link to your
  target, configured once with your install option OFF (fails) and once ON
  (passes).
- This is the embedding case where an install option defaulting to
  `PROJECT_IS_TOP_LEVEL` is off and should not be. Default it ON, let the parent
  opt out, and document that the parent's `cmake --install` will then also install
  your headers, library and package files into its prefix — plus every dependency
  target you bundle.
- A build-tree `export(EXPORT ...)` avoids installing either side; probe it the
  same way instead of assuming it clears the requirement.

## Optional distribution surface
Mature libraries ship some of these; each is a gap to report, not an embedding
blocker: pkg-config `.pc` files ({fmt}, Catch2), `install(TARGETS ... COMPONENT ...)`
plus CPack, the LICENSE installed alongside the headers, a build-tree
`export(TARGETS ...)` so a parent can export its own targets that depend on yours
without installing you, a CI workflow (the templates declare GCC/Clang/MSVC
support but nothing verifies it, and an install + `find_package` smoke job is the
cheapest way to keep the export surface honest), `CMakePresets.json` so local and
CI configure identically, and a stated version policy.
